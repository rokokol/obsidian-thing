What the server allows, and what it stops

Five separate mechanisms stand between an agent and a file. Each answers its own question, and none replaces another

Canonical source: docs/config.md, docs/vault-rules.md, docs/checker.md

The allowlist: which paths exist for this token

The allowed list is not a filter on results: it decides what exists at all. A file allows itself alone, a directory allows its subtree, and . opens the whole vault

[vaults.notes]
root = "/srv/notes"
allowed = ["Notes", "Projects/2026", "AGENTS.md"]
  • A hidden segment is always refused, and .obsidian is read only with read_obsidian = true
  • A symbolic link is refused: the server never follows one out of the vault
  • Every path in allowed must exist at start, or the server does not start
  • The same path resolution applies to a write, the index, the graph and search

The token: who is asking

One token opens one vault. The server reads it from the environment variable that token_env names and never stores it in the configuration

  • A wrong token gets 401, and an ID the configuration does not name gets 404
  • The metrics token must differ from every vault token, or the server refuses to start
  • read_obsidian = false removes access to .obsidian, which can hold plugin credentials

The revision: what the edit was built on

A revision is the SHA-256 of the file bytes. A write must name the one it read, or the server refuses: there is no blind overwrite

What each writing tool does
Tool Behaviour
writeCreates a file without expected_revision. An existing path is refused: read first, then replace
updateReplaces old with new where old occurs exactly once. Overlapping matches refuse as well
renameStays in the directory, keeps the extension, edits the visible links and never overwrites a target
deleteOnly into a configured trash, and only when no visible note would lose a link target

The replacement is atomic: the text goes to a temporary file beside its target and is renamed over it. One server process serializes its own edits, but it cannot see an unsaved buffer in Obsidian or a second writer

The trash: what a deletion leaves

trash_dir is a private directory outside every vault, on the same mount, so the move never crosses a file system

  • The server creates <trash_dir>/<trash_id>/file and, beside it, path with the original vault-relative path
  • Restoring means moving file back without overwriting an existing file
  • The server never purges the trash: the owner decides when to empty it
  • A path named directly in the allowlist cannot be deleted, because the server needs it at start

The vault rules: what counts as a mistake in the text

Each check compares the current file with the proposed text. A violation the file already had becomes a warning, and a new one blocks the write

  • Quotes, a final period, inline tags, callout markers, formulas in headings, links and hard wraps, each behind its own switch
  • Canvas and Base are checked structurally whenever their integration is on
  • The reply carries at most ten warnings unless all_warnings = true is passed

The checker: your own check before the write

A trusted script receives one JSON object with the operation, the path, the text before and after, the links and the selected properties, and answers allow, warnings or reject

  • A timeout, a non-zero exit, a malformed answer or more than 16 KiB of output blocks the write
  • The checker returns no replacement text and takes no part in a deletion
  • The script lives outside every vault, the trash and the state directory, and receives no variable that holds a token

Integrations: what else a switch needs

An integration that needs .obsidian access or a write refuses on a read-only vault, and the server does not start with that combination
