How the server is arranged

One process reads a TOML file and mounts an endpoint for each vault. Each endpoint has its own token, its own allowlist and its own set of tools. Nothing is shared between vaults except the process

The three things a client needs

01

The endpoint

http://127.0.0.1:8765/vaults/<vault_id>/mcp. The vault ID is the name of its table in the TOML file

02

The token

Authorization: Bearer <token>. The server reads it from the environment variable that token_env names

03

The access

The list of paths in allowed. A file allows itself, a directory allows its subtree, and . opens the whole vault

What happens on a call

The server holds no session: Streamable HTTP is stateless here, and every POST carries its own token. A call can therefore be repeated without restoring a handshake

  1. The transport compares Host with allowed_hosts and the token with the vault's bearer. A wrong one gets 401 or 421
  2. The tool resolves the path and keeps only what the allowlist permits and what is neither a hidden path nor a symbolic link
  3. A read comes from disk, a search from the local index, and a write to a temporary file beside its target
  4. Before it replaces the file the server checks the revision, the vault rules and the checker, and only then renames the temporary file
